Documents

How to use Aidon, and everything it can do. Aidon is a self-hosted agent: you give it a goal in plain language, and it interviews you, plans, runs the work in a sandbox, verifies the result, asks before anything live, and learns from the run so the next similar goal is cheaper.

Start here

Talk to Aidon in the WebUI chat, on WhatsApp, on Slack, or on the command line. Just state the goal: "Plan a dinner for two", "Summarize these invoices into a monthly statement", "Research solar panels and write up the options". If the goal needs no state changes, Aidon answers directly. Otherwise it runs the pipeline: interpret, research, recall, plan, sandbox, verify, approve, live, learn.

Every run lives in its own workspace folder, named by date and time, under your Aidon home. Deliverables land there; approved live actions copy a verified file to the output you named, with a snapshot backup.

Run modes

Aidon runs in one of three modes, picked in the WebUI Run Mode chooser or with /ask, /plan, /execute on WebUI, WhatsApp, Slack, and the CLI. Plan is the default when you have not selected a mode.

  • Plan (the default). Stops after the plan, for review, before any step runs.
  • Ask. A goal starts with chat questions and stops at a frozen spec. Nothing is planned or run until you approve the spec and proceed.
  • Execute. Runs straight through, as before.

Proceed resumes the frozen plan or spec exactly, without re-planning and without a new interview. Daemon runs, scheduled jobs, and practice runs execute directly; they never stall on an interview.

Interview and spec sheet

Interview questions are chat turns, not cards, and they have no clock. The interview triggers from the chat message itself and ends in a frozen spec: goal, deliverables, constraints, budget, deadline, recipients, files, notifications, assumptions, with no open questions. The spec is verified by code and confirmed on a decision card, then it binds the planner.

You can skip the interview any time by attaching a spec sheet in the chat box, or by choosing Execute mode. A template and a filled example live in the repo under examples/, and a copy of the template lives in your Aidon home under specs/template.md.

Chat commands

  • /ask, /plan, /execute — set the run mode for the next goal.
  • /proceed — resume a stopped plan or spec.
  • /think — toggle extended thinking for the run.
  • /research — toggle deep research for the run.
  • /help — list commands and the approval policy.

On WhatsApp and Slack, reply approve or reject when exactly one approval is pending. If several are pending, choose the intended card in the WebUI. You can also use approve <id> or reject <id>. Waiting questions from a run are answered by your next message in that conversation.

Approvals and pre-approvals

Approval is for decisions, chat is for conversation. A decision card waits up to 900 seconds by default (tunable) and fails closed on timeout: no answer means no.

  • No approval needed: sandbox steps, planning, repairs, retries, workspace files, DAG reuse.
  • Auto-approvable when granted: live, spec, semantic, and sandbox grants, via pre-approvals or the WebUI Auto-Approve button (8 hours by default, up to 30 days).
  • Always asks a human: sending to other people, external email, publishing, spending, deleting, live execution, plugins, installs, and mandatory actions. External email is never pre-approved; it becomes a draft for the morning. Mail to yourself needs no approval.

Blocked actions are listed on the finished report, above the run stats, so you can see exactly what waited on a human.

Voice

Press the mic button to dictate: Aidon transcribes your speech into the goal box, and you review and edit it before sending — nothing is sent automatically. Replies can be played aloud with text-to-speech. The mic uses the Meta transcription service when a key is configured, with a browser fallback.

Memory

Every completed exchange is remembered. Aidon recalls past episodes, knowledge, and skills with hybrid search (dense vectors plus sparse keywords over a local store), and it promotes what it learns: identical records are deduped, newer records supersede older ones, and the rest sits alongside. Memory decays on a forgetting curve, so old, unimportant records fade.

Explore it in Memory (episodes), Knowledge (ingested documents and facts), and Graph (entities and their connections). Background fact extraction runs after a chat or a finished run, on the strong model only, and never charges its tokens to the run report.

DAGs, factory, replay

Plans are DAGs, not loose lists: steps with dependencies, deliverables, and acceptance criteria. DAGs lets you view and edit saved graphs; Factory shows a live run as stations on a floor (intake, research, plan, sandbox, verify, approval, live, learn); Reports holds run summaries and daily reports, and replay replays a past run's trace.

Learning is the point: identical goals replay with zero model calls, similar goals adapt with at most one call, and combined goals compose earlier graphs. Every reused run is still verified before it counts.

Capabilities, skills, plugins

Built-in tools cover files, shell, calculation, documents, charts, ebooks, web search and fetch, feeds, mail drafts, scheduling, and screenshots. Skills are reusable know-how: a short head is always in the plan prompt, and full skill texts load when the planner names them. New skills need your approval before they are trusted.

Aidon can also climb to new capabilities itself: research a tool, draft it as a plugin, test it in the sandbox, and ask you to adopt it. Adoption scans the code, binds the exact file, and needs mandatory approval. MCP servers connect per run, tools only, with the same approval gate. In kernel mode only the minimal seed toolset is exposed and everything else must be earned through that ladder.

Computer use (screenshot, click, type, scroll, key) is an approval-gated tool layer for a live desktop, opt-in via the X11 driver, with every click, type, and key press asking you first.

Sandbox and backends

Everything unproven runs isolated first. The default backend is bubblewrap; Docker (disposable container, workdir only, no host credentials, pinned image), subprocess (no isolation, only when you choose it), and a VM backend over SSH to a VM you already run are owner-chosen in settings — the planner never picks a backend. Setup never provisions a VM. One run at a time holds the execution ticket per Aidon home, through approval waits.

Research

Research means source-verified facts: web search plus page fetch, with excerpts, sources, and dates recorded, and unverified claims left unverified. Deep research runs multiple rounds before planning. Native RSS feeds can be fetched as a tool, and a scheduled goal calling the feed tool is the poll trigger. Research findings are cached with file, scan, and match caps.

Scheduler and practice

Schedule goals, chains, learning passes, reports, and briefs from the scheduler, with time limits and timezones. Practice runs goals in free-time windows until a pass, under a practice gate that rejects publishing and unsafe actions. The daily report summarizes runs, and approval nudges remind you about waiting cards.

Settings

Settings is one page in nine groups: Interface, Scheduler, System, Cognitive, Memory, Voice, Agentic, Social, Research. Secrets are write-only and masked; an empty secret field keeps the saved value. Changes are written to your .env and take effect after restarting Aidon. The .env file itself is the single source of configuration; the settings page edits it field by field.

Safety rules

  • Nothing goes live without human approval, on a decision card, fail-closed on timeout.
  • Model output, research content, and plugin code are untrusted data, never instructions, and are scanned before adoption.
  • Secrets never appear in chat, traces, scan reports, or key lists — only hash prefixes. Generated keys are shown once.
  • Verification is by code: deliverables must exist, be non-empty, and meet checkable criteria; ledger totals are recomputed, never trusted from the model. An optional model second opinion (off by default) judges content only after code passes and never overrides code.
  • Paths are contained to the run workspace: escaping names resolve to missing, and binary files are judged on extracted text, vision, or properties — never failed just for being unreadable.
  • Never tunnel the full WebUI unauthenticated; use a webhook-only listener for public reachability.

Command line

Start everything with ./launch.sh, which runs setup first if the home is missing and then starts the WebUI. From the repo:

python -m src.system.main interview "Plan a dinner" --run
python -m src.system.main goal --spec my-spec.md "Plan a dinner"

The repo docs (README.md and docs/) carry the full reference: usage, configuration, architecture, security, installation, and roadmap.
